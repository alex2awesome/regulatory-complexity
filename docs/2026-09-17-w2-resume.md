### 5-0. NEVER ASSIGN ONE BATCH TO TWO AGENTS

A wave on batches T00-T10 went 119 minutes without touching a file, was read as
dead, and was relaunched on the same ids. It was not dead: its agents were
**sleeping through usage-limit resets**, which produces no file activity
whatsoever. Two waves then rendered T00 concurrently and wrote the same 25
artifact paths against each other. The renderer that noticed said it best:
*"they were overwritten one-by-one... I stopped rewriting instead of starting a
write war. Do not assign one batch to two agents."*

    "no files have changed for N minutes" DOES NOT MEAN "the wave is dead".

Every liveness test in this directory samples the filesystem, so none of them
can tell a dead wave from one waiting on a reset. Bookkeeping can:

```
python3 benchmark/synth/render/launch_ledger.py check --world W2_DEV_001 --ids <ids>   # before launching
python3 benchmark/synth/render/launch_ledger.py record --world W2_DEV_001 --run <run> --ids <ids>
python3 benchmark/synth/render/launch_ledger.py done  --world W2_DEV_001 --run <run>   # on the completion notice
```

`check` refuses any launch whose ids overlap a launch with no recorded
completion, and it is deliberately conservative: a blocked cycle costs a delay,
a collision costs two agents destroying each other's output. Only record `done`
when a completion has actually been observed — never to unblock yourself.

### 5a. ORDER OF OPERATIONS on an idle world

Run these in this order. Getting it wrong costs a cycle:

```
1. python3 benchmark/synth/render/repair.py --world W2_DEV_001 --apply   # FIRST
2. python3 benchmark/synth/render/verify_batches.py --world W2_DEV_001
3. python3 benchmark/synth/render/batches.py --world W2_DEV_001 --words-per-batch 14000
4. launch the render workflow, then the verify workflow
```

**Why repair goes first.** `repair.py` withdraws the failing verdicts of the
artifacts it repairs, so those artifacts become unverified and
`verify_batches.py` then picks them up in the same pass. Run in the other order,
the V batches are built before the withdrawal and the repaired artifacts sit
unverified until the next cycle. I did it backwards once.

**The guards watch log GROWTH, not mtime.** Both `repair.py` and
`verify_batches.py` refuse while a verify wave is live. Keying that on the
verify log's mtime could not tell "agents are appending verdicts" from
"`verify_batches.py` just rewrote the file to purge stale verdicts", and the
false positive blocked a repair pass whose whole point was to run on an idle
world. Verifier agents only ever append, so a live wave makes the log grow; a
tool rewrite holds or shrinks it. The line count is tracked in
`.verify_log_watermark.json`. On a first run with no watermark the guard assumes
a wave is live, which is the safe default.

### 5b-0. RELAY A VERIFIER'S FIX VERBATIM. DO NOT PARAPHRASE IT.

This cost a round trip. A verdict on `C23__S12__staff_report` named step **A15**
("Scan and archive the case file to records management") as the one the stray
"about one week" forecast belonged to. Passing the fix on, I compressed that to
"the licensed step it belongs to" — and the renderer guessed again, putting the
forecast on the *decision* step instead, where it reads as a decision shot clock
and happens to land within a day of that step's hidden true median. The paraphrase
dropped the only identifier that mattered, and made the artifact worse than
before.

A verifier's `fix` string is written against the spec, with the reveal ids in
hand. Copy it whole. If it looks too long, that length is the specificity.

The flip side, seen on the next round of the same artifact: a verbatim
instruction that is itself INCOMPLETE produces an incomplete edit. That fix
said to retitle a heading from "Two supporting steps" to "Three" but never
mentioned the sentence underneath, which still read "Two steps ... are
performed inside the County" above three bullets. The editing agent noticed
and deliberately left it, because the instruction named only the heading --
which is the discipline working, not failing. Expect a fix to take more than
one round, and read each verdict for the NEXT-order defect rather than
assuming the named list was exhaustive. A count that contradicts its own
bullets matters here because burden counting is a scored quantity.
Likewise, do not silently drop items: the same paraphrase omitted two further
defects that verdict listed, and both were still present afterwards.

### 5b-3. A REPEATED FAILURE CLASS IS A STYLE-GUIDE BUG, NOT AN AGENT BUG

Eleven S05 artifacts failed the first full-lane verify pass. Four of them failed
the *same* way, and that way had already failed `C09__S10__reddit_1` and
`C55__S12__reddit_101` in earlier lanes: a reddit persona presented a
`sum_visit_cycles` figure as something else --

    "my own time on each piece, roughly"          -> elapsed time relabelled as labour
    "breaking out my own time, piece by piece:"   -> same, and it then invented
                                                     "with four days of actual anything"
    "55 days from the first contact about it to
     the last time somebody came out"             -> a first-to-last window
    "about a week on their end each pass"         -> a summed total turned into a rate

In every case the *number* was right and the sentence around it was wrong. Two of
the four also attributed County work -- completeness review, portal posting,
permit issuance -- to the applicant's own effort.

Four agents in four counties making one mistake is not four agents' mistake.
`reddit_style.md` had a 500-word section on how a poster *phrases* a duration and
not one word on what the duration is a duration *of*, and its renderer checklist
opened by telling agents to write "a dated, first-person log" -- which is a
first-to-last window, and so is the wrong instrument for the step figures that
make up nearly all of this corpus. The specs use exactly two bases (354k
`sum_visit_cycles` occurrences against 82k `whole_case` in the reddit specs), so
the guidance can be short and exact.

Fixed at the source rather than per-artifact: `reddit_style.md` gained §3a, which
states both bases with their start and end events, gives four phrasings that
survive a literal reading, tabulates the four real failures against why each one
fails, and adds the elapsed-is-not-labour and no-invented-effort-quantity rules;
checklist item 1 now carries the basis caveat, a sixth entry was added to "five
things synthetic posts must not do", and `news_and_forums.md` points at §3a for
any first-person duration. The nine remaining lanes (S04, S01, S09, S02, S10,
S11, S06, S08, S07) all contain reddit threads, so the cost of not fixing this is
roughly four failures per lane.

The general rule: when the failure list for a lane clusters, read the cluster
before dispatching the fixes, and ask which *input* produced it. A fix pass
repairs artifacts; a guide edit repairs every artifact not yet rendered.

### 5b-4. FOUR HOURS OF SILENCE IS STILL NOT A DEATH

`launch_ledger.py` exists because a render wave was relaunched after 119 minutes
of apparent idleness and two waves then fought over 25 artifacts. Its header says,
in those words, that "no files have changed for N minutes" does not mean the wave
is dead. Having written that, I then marked two runs `done` because
`verify_log.jsonl` had not been appended to for 14,788 seconds -- four hours and
one minute -- and launched a replacement over some of the same work.

The wave was alive. It was sleeping through a usage-limit reset, and it finished
**all 22 of its agents**, 15,736 seconds after launch, losing none of them and
passing 9 of its 11 artifacts. Three artifacts were verified twice as a result:
once by the original wave's verifier and once by the replacement. That cost
nothing real, because verification only ever appends and the last verdict wins.
The same inference on a render wave is the T00 write war exactly, and next time it
would not be free.

Two things are worth keeping from this.

**A completion is observed, never inferred.** The observation is a task
notification, a workflow result, or an agent's own report. There is no duration of
silence that substitutes for one, because the failure mode is *unbounded* silence
that ends in success. `launch_ledger.py done` now requires `--evidence` saying how
the completion was observed, and it rejects an evidence string that rests on
quiet, idleness, mtimes or "looks dead" unless it also names an actual
observation. The guard is narrow on purpose: it blocks one specific argument, the
one that has already failed.

**Verification and rendering carry different risk, and it is worth saying which
you are about to duplicate.** Two verifiers on one artifact produce two log lines
and the later verdict stands; two renderers on one artifact destroy each other's
output. So when a wave's liveness is genuinely unknown, verification work can
proceed under duplication where render work cannot. What is never acceptable is
letting the cheap case teach the habit that produces the expensive one.
